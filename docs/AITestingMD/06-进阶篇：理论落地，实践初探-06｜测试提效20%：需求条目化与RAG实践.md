## 测试用例生成的提示词探索

在最开始尝试利用大模型生成测试用例的时候，重点可以聚焦在如何写提示词让大模型使用不同方法设计测试用例上，就像前面我们举过使用提示词完成等价类划分法设计测试用例的例子，除了这个等价类划分法设计测试用例以外，我还尝试利用思维链完成因果图测试用例设计的提示词，如下所示：

```perl

                    在使用因果图测试用例设计方法的时候重点分析出所有输入和输出条件的相互制约关系及组合关系，输
                    出对于输入的依赖关系也就决定了什么样的输入组合产生什么样的输出结果。####
                    因果图中条件和结果，也就是输入和输出之间有四种关系分别是恒等、非、或、与。####
                    因果图中条件和条件之间有五种关系，也就是输入和输入之间有五种关系分别是互斥、包含、唯一、要求、屏蔽。####
```

上面的提示词既可以直接在一些大模型的Chat应用中使用，也可以集成到代码中作为系统提示词使用。除去思维链的提示词方法，还可以用Chain Prompts方式将正交试验法设计测试用例的方法引入到测试平台中。

Chain Prompts是指在一个对话或文本生成任务中，将前一个提示的输出作为下一个提示的输入，形成一个连续的链条。这种方法常常用于创建连贯的、有上下文关联的文本。在对话系统中，这种方法可以模拟真实对话中的连续性，使生成的回复更加自然和流畅。下面我就给你讲讲Chain Prompts提示词是怎么工作的，首先借助大模型的能力，设计了一个提示词实现了为输入的每一个参数返回边界值，实现代码如下：

```perl
def generate_boundary_values(self, parameter_descriptions: List[str]) -> List[List[str]]:
        """
        生成参数边界值
        
        Args:
            parameter_descriptions: 参数描述列表
            
        Returns:
            边界值列表
        """
        if not self.llm:
            print("LLM未初始化")
            return []
        
        boundary_values = []
        delimiter = "####"
        
        for desc in parameter_descriptions:
            prompt = f"""{delimiter}你是一名资深测试工程师。
{delimiter}设计参数的边界值: {desc}
{delimiter}边界值要包含满足要求和不满足要求的内容，直接返回字符串数组，格式如：["value1", "value2", "value3"]
{delimiter}不要返回python代码，不要包含任何注释。"""
            
            try:
                print(f"正在生成参数边界值: {desc}")
                response = self.llm.invoke(prompt)
                values = self._parse_boundary_response(response)
                boundary_values.append(values)
                print(f"生成边界值: {values}")
            except Exception as e:
                print(f"生成边界值失败: {e}")
                boundary_values.append([])
        
        return boundary_values
   
```
利用大模型返回的边界值参数，识别出计算正交表需要的因素数、水平数，然后组织了一个新的计算正交表的Prompt，用大模型计算一个因素数是变量个数，水平数各个参数对应的值个数，强度是2的一个正交表，实现代码如下：

## RAG为测试用例生成铺平了道路

我们仔细分析后发现，最开始设计提示词的思路没有问题，但直接简单粗暴地把需求加上前面介绍的测试用例设计的系统提示词，喂给大模型就产生了问题，这里主要有两大问题：

* 问题一：需求管理系统中的需求千差万别，有的平铺直叙，一大段话很长很长，描述了全部的需求；有的一句话了事，简单概括，很多交付细节都是产品经理、开发工程师、测试工程师私下达成共识，这就导致了利用大模型生成测试用例的提示词内容不完善。

* 问题二：在设计测试用例生成的Prompt的时候，验证是否有效，使用的一些业务逻辑非常简单，实际工作中需要验证的业务逻辑要复杂得多，往往在实际的需求中只会介绍当前要实现的业务逻辑，但是系统中已经交付的业务逻辑，并不会在这个需求中再描述一遍，这也就导致了大模型并不理解系统中已经有的约束条件。


解决第一个问题的最好的方法就是**需求条目化**，第二个问题的最优解就是**RAG**，那么下面我就给你讲讲这两个方法都是如何实施的。

### 需求条目化

相信你接触大模型肯定总能看到数据标注、数据治理等字眼，那么需求条目化也可以理解成是真需求进行的数据标注，如果说是数据标注想必你就能理解了，我们并不仅仅是制定一个需求条目化的方法，让产品经理未来要这样写需求，而是也要把历史中的需求按照条目化的方法重新整理。


需求条目化听起来很高大上，其实就是一个“把大任务切成小菜谱”的把戏！假设今天晚饭你点外卖，只说“来份麻辣烫”——厨师就需要猜你是爱吃辣还是怕吃辣？条目化就是把这部分模糊的需求，细化成“辣度中辣，加牛肉不加豆腐”的清单，一条一条列清楚。核心是：把模糊需求拆成具体、可操作的小条目，让大家（开发、测试、老板）都心知肚明，不会走弯路。


那么对于一个大段文字描述的需求，怎么改写成条目化的需求呢？可以分三步进行：

1. 整体目标：先写整体需求。

2. 拆小条：分成输入、处理、输出、验证等模块，每条用1-2句话说清“做什么、怎么做、为什么”。

3. 加上验收条件：这是关键！每个验收条件后附上“怎么证明它OK了”，避免“做好了？嗯，差不多吧”这种尴尬情况。


这里的验收条件是一个需求条目化好坏的关键，验收条件（Acceptance Criteria，简称AC）就是“过关标准”，写它像写游戏关卡的规则：**具体、可测、可重复**。不写“快点做好”，要写“输入X，输出Y，时间<Z秒”。这里我特别推荐你使用Gherkin格式，也就我们常说的Given-When-Then的表达方式。Given是描述前提条件，When是描述操作，Then是描述结果。假设我准备周末去野营，如果没有使用条目化的方式列好需求清单，有可能就会被直播间的各种推销搞晕了头脑，买一大堆乱七八糟的装备，却没有买帐篷，那就惨了。那么如果我利用条目化方法整理了这次野营的需求呢？


就很清晰了：
![](https://static001.geekbang.org/resource/image/e3/78/e3793d6c1b82ffeff2c78cc53a24d578.png?wh=2290x1372)

* **准备装备**：买帐篷、睡袋、防蚊喷雾。**验收**：Given 清单齐全，When 打包测试，Then 重量<10kg，无遗漏。

### 用RAG让输出更准确

使用需求条目化完成全部需求的整理后，就为利用大模型生成实际可用测试用例奠定了基础。前面说的第二个问题就可以利用RAG和已经条目化改写的需求数据解决。


我们前面聊到生成测试用例的时候，导致生成测试用例的不全面、不准确的一个原因就是，输入的需要生产测试用例的需求描述，往往不会把所有相关的需求都再描述一遍，而是仅仅描述当前需要变更的部分。那么我们就可以利用RAG，将已经条目化改写的需求向量化存到向量数据库里面，这样我们每次生产测试用例的时候，就可以为本次的需求找到一些相关的历史需求，一起发送给大模型，这样生成的测试用例就会更加完善。

## 总结

这节课我们从理论转向实践，深入探讨了大模型是如何在测试用例生成中落地的。通过精心设计的提示词（如思维链用于因果图、正交试验的Chain Prompts），我们能高效生成覆盖多种设计方法的测试用例，但实际应用中，需求不完善和历史业务逻辑缺失往往导致输出脱离现实。


为此，我们引入需求条目化——以Gherkin格式拆解需求为清晰、可测的清单，确保输入的“菜谱”精准无误；同时，借助RAG技术，将条目化需求向量化存入知识库（如dify平台），检索相关历史上下文，补充非功能、安全等维度，让大模型输出更全面、准确。


这些内容中我想传递的核心思想就是使用大模型的过程要“思考先行”，绝非简单喂入需求。记住，条目化+RAG不仅是工具，更是思维框架，如果能直接转化为团队流程，起码可以提升20%的测试效率。
