DL包含了生成式模型（Generative）和判别式模型（Discriminative），判别式模型学习数据的边界和差异，用于分类或预测。例如，一个模型判断一张图片“是猫”还是“不是猫”，它就是在做判别。

# 测试工开发程师也需要了解Attention

相信所有开始接触LLM的同学都听说过Google的“attention is all you need”这篇论文。对于每一位测试开发工程师而言，理解这篇论文的基础内容才能让你工作中能更好地驾驭LLM。虽然我们不需要了解每一个算法的实现细节，但是我们要理清楚Attention机制。这就要从最开始的FNN的弊端开始谈起。下面我用老北京炸酱面的制作为例来讲一讲FNN、RNN、CNN、Attention机制，最后讲到Transformer的Self-Attention。

>你在做老北京炸酱面的酱，食谱包括一系列步骤：准备食材（干黄酱、甜面酱、猪肉、葱姜等）、洗菜、切菜（葱姜蒜等）、炒肉，调和干黄酱、甜面酱、凉水、酱油后，加入锅中，慢炖成酱。

## 新厨师：处理独立、静态输入的FNN

FNN全称是Feedforward Neural Network，**前馈神经网络**。FNN是最简单的神经网络，像一个完全新手的厨师，只看当前的步骤，没有前后步骤的记忆和关联。一个新手厨师第一次拿到菜谱后，就开始按照菜谱做饭，看一步做一步，每一步都是独立的，比如看到了“切葱”的步骤，就只看到切葱的输入“粗细、长短”等，输出就是“切成小段的细葱丝”。


他并不管前面的步骤，也不管后面的步骤。前面一步洗葱，但如果没有洗就切了，葱上会有泥。后面一步是用200度的热油炒香葱丝，那么如果葱丝切得很细，下锅就糊了。

![图片](https://static001.geekbang.org/resource/image/be/b0/beea25e428a51f55ba1414e87d04a6b0.png?wh=1286x682)
这就如同一个手忙脚乱的新厨师，只能按照每一步指令干活，只顾眼前。这样的优点就是每一个步骤都简单，适合独立步骤的任务。但是由于忽略步骤的连续性，如果食谱是“1. 洗葱；2. 切葱；3. 炒肉”，FNN把每步当独立任务，就可能导致错误：没洗就切，葱不干净；或切得太细，下锅一炒就糊了。


那么这炒酱是一个连续性的工作，FNN无法处理好这种有序列性的工作，就像新手不懂整体流程。这时候我们就需要一个能记住前因后果的模型——RNN。

## 有点经验的厨师：有序列记忆的RNN

RNN全称是Recurrent Neural Network，**循环神经网络**。RNN通过循环机制记住之前的步骤和状态，适合处理序列。这就像一个有点经验的厨师炒酱，能够根据前几步调整当前的步骤。


菜谱的步骤是这样的：

1. 洗葱姜蒜

2. 切葱姜蒜

3. 切肉

4. 炒葱姜蒜后捞出

5. 炒肉

6. 调和干黄酱、甜面酱、凉水、酱油

7. 加入锅中慢炖成酱


这个有点经验的厨师从头开始，在切葱的时候就已经记住了，葱是已经洗干净的了，并且知道切的葱丝不要太细，也不要太粗。炒葱、姜、蒜的时候就记住了葱、姜、蒜切的大小、粗细，从而知道炒多久捞出。加入调和的酱慢炖的时候，会综合前面的步骤控制时间，确保酱浓稠。这样有可能下一步输出“小火搅拌，防止酱粘锅”。

![图片](https://static001.geekbang.org/resource/image/0d/19/0dcdf39337a37c60f0ca8614ede49719.png?wh=1286x682)

RNN能处理顺序依赖，但是它的记忆能力有限，如果食谱很长，那么这个“有点经验的厨师”可能会忘记前面洗葱、切葱的步骤，而且他是一步一步地处理，效率低，不像一个经验丰富的厨师，先看完菜谱，然后胸有成竹地开始炒酱。做炸酱不仅需要记住顺序，还需要快速识别“局部规律”（如“切葱姜蒜+快炒”的搭配模式），这就需要CNN，它擅长找局部模式。

## 擅长找规律的厨师：捕捉局部规律的CNN

CNN全称Convolutional Neural Network，**卷积神经网络**。它是一个擅长找规律的厨师，关注菜谱中相邻步骤的模式，并不是记住做饭步骤的序列，而是找出相邻步骤的模式，它用“放大镜”扫描食谱，找出关键的组合技巧。


我们想象菜谱是一个很长的步骤列表。CNN就是一个拿着“放大镜”（这放大镜就是卷积核，Convolutional Kernel）的有经验的厨师，快速地扫描列表的片段，扫描到了“切葱姜蒜”和“炒肉”这一段的规律，是葱姜蒜切得细等长+大火快炒=爆香效果好，又扫描到“加调和好的酱汁”和“慢炖”，发现调和好的酱汁+慢炖并且不断搅拌可以做出香浓酱汁。

![图片](https://static001.geekbang.org/resource/image/d5/47/d5ec45b01da1aa38d31453517c111b47.png?wh=1286x682)

CNN抓住了关键的搭配秘诀，它注意到某些步骤总是成对出现，比如“切细葱姜蒜+快炒”总能爆香，或者“加调和酱汁+慢炖”总能让酱浓稠。就像老北京厨师传授的“炒肉前必须爆香葱姜蒜”的小技巧，CNN快速找出这些局部“套路”，无需关心整个食谱的顺序。


虽然CNN擅长捕捉局部，但它还是只看固定大小的局部（比如2步组合、3步组合），无法处理远距离的依赖，比如这个擅长找规律的厨师无法找出最开始选择猪肉的肥瘦对最终酱汁的口感的影响，他虽然关注了一些规律但是却忽略了全局。一个资深的厨师，需要动态地“聚焦”，比如炒肉时，重点回忆葱姜蒜的切法，而不是均匀看待所有步骤。CNN的固定窗口限制了灵活性，这时候我们的Attention机制就闪亮登场了。

## 资深厨师：动态聚焦关键步骤的Attention机制

Attention也叫注意力机制。它是一个资深厨师，能够动态关注食谱中最相关的部分，而不是按顺序或局部处理。它通过计算当前步骤与过去步骤的相关性，决定哪些步骤更重要。例如在做“慢炖”这一步的时候，这个资深的厨师会扫描整个食谱，计算哪些步骤对现在最重要。假设他发现切葱姜蒜的粗细会影响爆香，决定酱汁的香味，而调和的酱汁的比例会影响最后的黏稠度，就会把这两个步骤分配更高的权重。

![图片](https://static001.geekbang.org/resource/image/18/ab/18dyy814325530a78cbdb9d1f143d0ab.png?wh=1286x682)

Attention这个资深的厨师会快速地翻阅菜谱，然后找出关键点。这样就可以**灵活地处理距离依赖，不受序列长度的限制，并且是可解释的**（也就是可解释为什么要关注这些步骤）。传统Attention常用于“输入-输出”任务（比如翻译），需要外部“查询”（如当前步骤查询过去步骤）。但如果整个食谱是自包含的（步骤间自己关联），Attention需要外部引导，不够简洁。

## 特级厨师：全局自我关联的Self-Attention

**Self-Attention是Transformer的核心**，允许序列中每个步骤“自己关注”其他所有步骤，像一个大师级厨师，能让食谱的每一步都相互“对话”，形成全局优化方案。食谱的每个步骤（洗葱、切葱、炒肉、调和酱汁等）同时处理。

![图片](https://static001.geekbang.org/resource/image/98/73/98e55fe9e88f41787b303d0b2f865373.png?wh=1286x682)

Self-Attention让每个步骤“提问”：我跟其他步骤关系多大？比如“切葱姜蒜”会计算，跟“炒肉”关系强（直接影响爆香）；跟“慢炖”关系中等（影响酱的香味）；跟“洗葱”关系弱（只是前提）。整个食谱形成一个“关系网”，输出优化建议：因葱姜蒜切细，炒肉用大火，炖时少加盐，突出酱香风味。


多头Self-Attention还能从不同角度优化（一个头关注爆香时间，另一个关注酱料搭配）。这样全局关联、并行处理、高效；克服RNN的序列瓶颈和CNN的局部限制；适合复杂任务（如优化整个炸酱流程）。但是这个大师级的厨师计算量大（但现代硬件支持），需要大量训练数据。


到这里我们就把《Attention is all you need》这篇论文的主要内容讲解完了，具体的实现算法你可以随着工作慢慢消化。在理解了Self Attention的机制后，我们就从内转到外，聊一聊Tokens，无论是使用ChatBot模式的大模型应用，还是开发Agent都需要精细地算好Tokens这笔帐，否则就会让我们收获更多的幻觉。

# 理清Tokens这笔帐

想必Token这个词你已经听过很多次了，很多模型都给出了最大Token数量，但是Token到底怎么算的，下面我们就一起来聊一聊关于token的内容。


Tokens的计算其实是和具体的上下文、tokenizer（分词器）有关系，不同的模型会使用不同的tokenizer（如BPE、WordPiece、SentencePiece等），对 Token 与单词/字符的对应关系产生影响。我们可以粗略地用下面这种方式估算：

* 英文: 1 token ≈ 0.75 单词 ≈ 4 字符 

* 中文: 1 token ≈ 1-2 字符 

* 混合: 1 token ≈ 2-3 字符

## 英文：1 token ≈ 0.75 单词 ≈ 4 字符

在英文中，基于常用的 BPE（Byte Pair Encoding）分词器（如 GPT 系列使用的），1 个 Token 通常对应 0.75 个英文单词，这是因为英文单词可能被拆分为多个 token，例如，"playing" 可能被拆为 "play" 和 "##ing"，而短单词或标点可能单独成一个 token。1 token ≈ 4 字符也是合理的近似值，因为英文单词的平均长度（包括空格和标点）约为 5 个字符，但分词器会将常见单词压缩为单个 token，而较长的单词可能会被拆分。


OpenAI 的官方文档和实践表明，英文文本中 1 token 大约对应 4 个字符（包括空格和标点）。例如，"The quick brown fox"（4 个单词，20 个字符，包括空格）通常被分为 5-6 个 token，平均每个 token 约 3.5-4 字符。


在实际的工作中英文文档可以使用**4000 tokens ≈ 12000-16000 字符的等量关系进行估算，**英文文本中，空格和标点会增加字符数，而分词器可能将常见单词压缩为单个 token。OpenAI 的经验数据表明，4000 个 token 的英文文本通常对应 12000-16000 字符，尤其是在包含空格和标点的情况下。

## 中文：1 token ≈ 1-2 字符

在中文中，分词器通常将每个汉字视为一个独立的 token，或者将常见的词组（如双字词）合并为一个 token。因此，1 个 token 通常对应 1-2 个中文字符（汉字），具体取决于分词器的词表和文本内容。例如，短语“人工智能”可能被分为 2 个 token（“人工”和“智能”），或在某些优化分词器中作为一个 token。


以 GPT-4 的分词器为例，中文文本的 token 数通常接近字符数的 0.5-1 倍。1 token ≈ 1-2 字符是一个合理的估计，但更精确的范围可能因模型而异，例如，1 token ≈ 1.2-1.5 字符在某些模型中更常见。


在实际的工作中，中文文档的Tokens估算可以采用**4000 tokens ≈ 6000-8000 字符等量关系进行估算，**考虑到中文文本中可能包含标点、空格或短词组（可能合并为单个 token），6000-8000 字符是一个合理的范围。以实际测试为例，4000 个 token 的中文文本通常包含 5000-7000 个字符，具体取决于文本的复杂度和分词器的效率。


## 混合：1 token ≈ 2-3 字符

在中英文混合文本中，token 与字符的关系会受到两种语言特性的影响。英文部分可能每个 token 对应 3-5 个字符，而中文部分可能对应 1-2 个字符。因此，平均 1 token ≈ 2-3 字符是一个合理的估计，如果文本中英文占主导，平均字符数会偏向 3-4；如果中文占主导，平均字符数可能接近 2。实际测试中，混合文本的 token 数通常介于纯中文和纯英文之间。


对于中英文混合的文档，比较推荐你使用**4000 tokens ≈ 8000-12000 字符的等量关系进行估算。**实际测试中，4000 个 token 的中英文混合文本（假设中英文各占一半）通常对应 8000-10000 字符，具体范围取决于文本内容。


不同模型的分词器会导致 token 与字符/单词的对应关系略有不同。例如，BERT 的 WordPiece 分词器可能将英文单词拆分得更细，而 LLaMA 的 SentencePiece 可能对中文更优化。专业术语、缩写、标点密度等会影响 token 数。例如，技术文档可能有更多短 token，而文学文本可能有更长的 token。如果需要精确估算，建议使用具体模型的分词器工具（例如，OpenAI 的 tiktoken 库）来分析实际文本的 token 数。


# 超参知多少

超参数是指在模型训练或推理过程中需要手动设置、无法通过训练数据直接学习的配置参数。这些超参数控制模型的架构、训练过程、推理行为以及生成文本的质量和特性，影响模型性能、效率和输出效果。最为常见的就是temperature、top_k、top_p。

### temperature

temperature控制输出文本的随机性和创造性，通过调整模型预测的概率分布。通过缩放模型输出的logits（未归一化的概率）来改变softmax函数的概率分布。temperature设置越低（大概0.1到0.5），越能得到确定性的预测，temperature设置越高（大于1.0），越不能得到确定性的预测。temperature的Greedy Decode是0，永远选择概率最高的预测，但是这并不是说设置0就是永远输出相同的预测，最高概率的预测有可能不止一个。temperature较居中的设置（大概0.6-0.9），可以提供一个在确定性和创造性之间平衡的预测。

* temperature的改变是非线性的，在相对较小的区间内修改temperature的值（例如0.5-0.6），对于预测的影响要远远大于在temperature在较大的区间修改（例如1.5-1.6）。

* 绝大部分的模型框架temperature是在其他的top_k、top_p、min_p之后起作用的。因此比较推荐优先调整其他的参数，尤其是使用了llama.cpp框架的时候。

### top_k

top_k，从概率最高的k个词中随机采样，限制选择范围以平衡随机性和质量。top_k 值越高，模型的输出越具创造性和多样性，top_k 值越低，模型的输出越受限制和基于事实。top_k为1是Greedy Decode。在llama.cpp中，采样参数的优先级是top_k、top_p、min_p，所以top_k是最先被满足的。

### top_p

top_p（nucleus samoling），根据累积概率阈值p动态选择采样词集合，增加输出的多样性。top_p的值范围从0（greedy decode）到 1（LLM 词汇表中的所有Tokens）。但是top_p优势也会有一些潜在风险。

* 扁平分布：当token的概率分布比较分散，top_p可能会包含很多低概率的tokens才能达到阈值，因此导致不一致。

* 峰值分布：当只有一两个tokens的概率占据了99%的概率，那么结果就会选择这一两个tokens，从而影响了多样性。

* 缺乏适配性：不会根据模型在不同情况下的置信度动态调整候选集的大小。


除此之外还有min_p、惩罚函数（repeat_penalty、frequency_penalty、presence_penalty）、Mirostat、tfs_z、typical_p等，这些并不是很常见，遇见的时候你可以再去查一下，在我的经验中建议你尽量少用惩罚函数，所有超参的设置都是依据模型和要模型完成的任务而选择的，并不存在一个万能的公式。下面是几个我在开发一些基于大模型的测试工具的时候曾经遇到过的问题以及通过调整超参解决的办法，希望给你以后在开发或者使用大模型的测试工具的时候提供点帮助。


### 调参


在和模型交互过程中，如果模型一直重复反馈相同内容，可以稍微增长一点min_p（例如增长到0.1），或者增长top_p到0.85，过滤掉一些由于低概率的tokens导致的循环。在这个调整过程中如果temperature设置得比较高，可以尝试降低一点（例如降到0.7、0.8）。


如上调整如果还不起作用，可以尝试调整惩罚函数repeat_penalty（推荐尝试1.05、1.1，最大1.15或者1.2），然后在测试过程中查看是否有“幻觉”。如果还不起作用，可以尝试设置frequency_penalty（推荐尝试0.1-0.5），减少重复使用的tokens或者使用presence_penalty（推荐尝试0.1-0.5）减少上下文的重复tokens。


如果在测试模型的过程中发现模型反馈的内容太随机，相关性很差，首先应该检查top_k是不是设置成了0，如果不是，可以通过增加一些temperature参数的设置再进行测试。如果效果不明显，可以尝试降低min_p（推荐尝试0.05或者0.03）。


如果发现模型在一本正经的胡说八道，那么可以调小temperature（推荐尝试0.3，甚至0.1），如果并无改善可以尝试增加min_p（推荐尝试0.1或者0.15）。


当然，这些调整超参的办法也并不见得一定有效果，在调整超参的同时也要关注其他方面，例如提示词里是不是有了一些对应现象的描述，上下文是不是挤爆了Tokens长度或者是模型本身就有对应现象的问题。



# 总结

今天的内容就到这里了，我们一起学习了一个测试开发工程师应该掌握的LLM基础内容，我们聊了炸酱版本的FNN、RNN、CNN、Attention以及Self-Attention，一起算了Tokens这笔不好算的账，最后学习了可以控制模型效果的超参。这些内容洋洋洒洒的，可能你能记住得并不多，但是下面几点你一定要烂熟于心：

* **理解LLM核心机制以优化策略**：测试开发工程师需掌握LLM的核心机制，如FNN的独立处理、RNN的序列记忆、CNN的局部模式捕捉、Attention的动态聚焦及Self-Attention的全局优化，这样可以更好地利用LLM在序列任务（如对话连贯性）或复杂依赖（如长上下文推理）中的表现，根据场景选择合适的模型机制，确保生成质量。

* Token是LLM处理文本的单位，不同语言的Token计算方式不同（例如，英文1 Token ≈ 0.75单词 ≈ 4字符；中文1 Token ≈ 1-2字符）。**测试开发工程师需掌握Tokenization以评估模型的上下文限制和效率**，尤其在混合语言场景下，可使用如OpenAI的tiktoken工具对Token进行精确计数。

* **超参数调优对模型行为的影响**：超参数如temperature（控制输出随机性，0.1-0.5偏确定性，>1偏创造性）、top_k（限制采样到概率最高的k个词）、top_p（核采样增加多样性）显著影响LLM输出。测试开发工程师需通过调整这些参数解决重复输出（如min_p增至0.1或top_p增至0.85）或不连贯输出（如temperature降至0.3）等问题，同时结合任务需求和模型特性进行优化。
